## Findings (8 max)

### 1. BLOCKING: Non-monotonic parent timestamps may produce non-deterministic merge ordering
- **Location:** Merge rule in `packages/core/src/parse.ts`/`analyze.ts`: "subagent events are inserted into the prompt's event sequence by timestamp: each subagent event goes after the last parent event whose timestamp is <= its own (ties: parent first); events without timestamps inherit the previous known one; subagent events earlier than the prompt start attach at the start, later than the end at the end. Parent events keep their relative order (no global re-sort, because parent timestamps are non-monotonic in ~7% of cases)."
- **Detail:** The merge rule processes events in input order and inserts subagent events relative to parent timestamps. If parent timestamps are non-monotonic (occurring in ~7% of cases), the "last parent event whose timestamp is <= subagent's timestamp" depends on the scan direction and prior events, which can lead to different merge outcomes for the same logical event sequence if the input ordering changes. The plan's "no global re-sort" avoids a full sort but does not guarantee deterministic ordering when the same events are presented in different input orders.
- **Fix:** Define the merge as a two-pass algorithm: (1) collect all events (parent + subagent), (2) perform a stable sort by timestamp with parent-first tie-breaking, using the original input index as the stable key to preserve order for equal timestamps. Document that the input event sequence must be in chronological file order for deterministic output.

### 2. WARNING: Async agent task-notification may arrive after prompt already classified, causing retroactive status changes
- **Location:** Async agent handling; plan notes "async agents return early in the parent (toolUseResult.isAsync, outputFile) and finish later (task-notification)".
- **Detail:** The merge rule inserts subagent events by timestamp, but there is no guarantee that a task-notification arriving well after the prompt was already classified (status/reason determined and UI rendered) will be retroactively applied. If the analyzer's status rule is evaluated only at parse time and not re-evaluated when new subagent events arrive, async agents' edits/checks may be silently dropped or, if re-merged, may change the prompt's status/reason after the fact — creating a race between live display and background completion.
- **Fix:** Ensure that async agent events are either (a) capped to the prompt's start/end timestamps so they never affect classification after the prompt is finalized, or (b) the analyzer re-computes status/reason whenever a new subagent event is merged for a prompt that was already finalized, with a flag indicating "post-classification update." Alternatively, treat async agent output as partial (`partial: true`) with reason suffix "; subagent activity not verified (async)".

### 3. WARNING: 100 subagent files / 1 MB each = 100 MB detail text; streaming may not prevent memory spikes during merged-event processing
- **Location:** Caps section: "per session 100 subagent files; per transcript 20,000 normalized events and 5 MB of retained detail text"; cost control: "analysis time for a session with 100 subagent files of 1 MB each must stay < 3 s (perf test with synthetic files)".
- **Detail:** The plan caps total retained text at 5 MB per transcript and 100 files per session, but does not cap the *merged* event sequence size before caps are applied. If all 100 subagent files have 20,000 events each, the merged sequence could exceed 2M events before truncation. The "analysis time < 3 s" perf test measures CPU time, not memory; a streaming read may still buffer all merged events in memory before the cap-check step, causing OOM on sessions with many large subagent files. The plan's memory model is underspecified for the worst case.
- **Fix:** Apply per-prompt event caps *during* the merge stream, not after: as each subagent event is inserted, increment a per-prompt counter; once 20,000 events are merged for that prompt, set `truncated: true` and cease inserting further events from any subagent transcript for that prompt. Add a memory-profiling step to the perf test that asserts heap usage < 150 MB with 100 files of 1 MB each.

### 4. OBSERVATION: ETag/cache key inclusion of subagent files may cause unnecessary 200 responses for incremental subagent progress
- **Location:** Critical implementation detail: "ETL keys of the HTTP API must include the subagent files' (path, mtime, size) so live refresh sees subagent progress (extend etagFor inputs and the analysis cache key)."
- **Detail:** The plan directs extending the ETag computation to include subagent file (path, mtime, size) alongside session file mtimes. However, a subagent file's mtime may change every poll cycle as the agent appends events, even if the *content* within the 20k-event/5MB cap has not changed meaningfully. This would cause every poll to return 200 with full re-analysis, defeating the purpose of conditional requests (ETag/304) and adding unnecessary CPU load. The plan does not distinguish between "file touched" and "content changed within cap" ETag triggers.
- **Fix:** Compute a two-part ETag: a "base" ETag from session file mtimes (unchanged for live refresh when only subagent progress occurs) and a "subagent delta" hash of the event count + last-event timestamp within the cap. The 304 response should be retained if the base ETag matches; a 200 is returned only when the subagent delta changes. This preserves the "idle poll (304) costs a stat per session file only" guarantee.

### 5. OBSERVATION: "partial" flag semantics inconsistent between transcript-not-found and transcript-truncated/capped
- **Location:** Partial/stays-true logic: "partial stays true only when an Agent tool_use has no found transcript (missing file, depth > 3, or truncated by caps). Reason suffix "; subagent activity not analysed" only then; when transcript found but truncated: "; subagent transcript truncated"."
- **Detail:** The plan distinguishes three partial causes: (a) missing file, (b) depth > 3, (c) truncated by caps. However, the UI reason text may not differentiate them clearly. More importantly, "truncated by caps" could mean either (i) the 20,000-event cap was hit or (ii) the 5 MB detail-text cap was hit, and the plan does not specify whether the reason suffix changes based on which cap was hit. The audit after S-11 found 13/22 prompts with Agent calls were wrong in status or reason, suggesting the partial/hedge logic already has gaps that may worsen with the expanded cap semantics.
- **Fix:** Add explicit test cases for each partial trigger: (i) missing subagent file → reason "; subagent activity not analysed", (ii) event count hits 20,000 → reason "; subagent transcript truncated (event cap)", (iii) detail text exceeds 5 MB → reason "; subagent transcript truncated (text cap)", (iv) agent depth > 3 → reason "; subagent activity not analysed (depth > 3)". Verify the reason text in the UI matches the trigger.

### 6. WARNING: Subagent file matching fallback may misattribute activity to the wrong prompt
- **Location:** Matching section: "a subagent file with no matching parent call is attached to the prompt containing the closest preceding parent event by timestamp (fallback) with a Warning 'unmatched subagent'."
- **Detail:** The fallback attaches an unmatched subagent file to the prompt with the closest preceding parent event by timestamp. In a session with many prompts close in time, or where a subagent's toolUseId accidentally matches a parent event from a different prompt's context (e.g., same timestamp, same agentType), the activity (edits, checks) could be misattributed, leading to incorrect status/reason for the wrong prompt and silent drops for the actual spawning prompt. The plan does not include a confidence threshold or secondary matcher (e.g., matching on description text, toolUseId frequency, or session structure).
- **Fix:** Before falling back to closest-preceding-parent, check for a stronger match: (a) subagent meta `description` (first user record, truncated to 200 chars) contains a keyword from the prompt's task description, or (b) the subagent's `toolUseId` appears in the prompt's own `Agent` tool_use records (if any), or (c) the subagent file's timestamps span a range that uniquely identifies its parent prompt. If no strong match, emit the "unmatched subagent" warning and keep the subagent events unattributed rather than assigning them to a potentially wrong prompt.

### 7. OBSERVATION: Node-free core claim must be verified for subagent parsing pipeline
- **Location:** Plan emphasis: "Core stays node-free: the core API takes already-parsed transcripts (createAnalyzer({subagents}) or analyzer.addSubagent(toolUseId, lines | events)). Core node-free grep rule unchanged; node IO under src/node/."
- **Detail:** The plan reaffirms the node-free core guarantee but the subagent parsing pipeline introduces new types (`SubagentTranscript = {agentId, description, events: Event[] (normalised, capped), truncated: boolean}`) and operations (matching `toolUseId`, streaming subagent JSONL files, normalising records with `isSidechain: true`). If the normalization step uses Node.js built-ins (`fs`, `path`, `os`) or regular expressions that depend on platform-specific path separators, the node-free guarantee is violated for core consumers. The plan says "node IO under src/node/" but does not audit the core `parse.ts`/`analyze.ts` subagent code paths for hidden Node dependencies.
- **Fix:** Audit the core `packages/core/src/parse.ts` and `packages/core/src/analyze.ts` subagent code paths: ensure all file reading uses paths already provided by the caller (the node layer), all string/path operations use plain JavaScript (no `path.basename`, `path.sep`, etc.), and all regexes are platform-agnostic. Add a `pnpm check` rule that flags any `require(` or `import` of Node.js built-ins in `packages/core/src/` except from test fixtures.

### 8. WARNING: Real-log audit target ≥97% may be unrealistic given S-12's complex merge logic on top of an already 90.8% baseline
- **Location:** Phase 3 success criterion: "Overall status match on the owner's real logs >= 97% (population B of the audit) and non-subagent population not regressed (>= 97.1%)."
- **Detail:** The audit after S-11 (without subagent tracking) had 90.8% status match across 120 turns. S-12 adds complex merge logic (timestamp insertion, non-monotonic handling, nested subagents up to depth 3, event caps, partial/hedge rules) that could introduce new classification errors. The audit fact "13 of the 22 prompts with an Agent call are wrong in status or reason" indicates the subagent classification space is already error-prone. Achieving ≥97% overall status match with the added complexity may require the Phase 1 fixture pass rate of 100% and extensive real-log validation across multiple user projects, not just the owner's logs. The "non-subagent population not regressed (>= 97.1%)" gate is necessary but may not be sufficient if the subagent merge logic interacts unexpectedly with existing check/edit heuristics.
- **Fix:** Lower the Phase 3 target to a realistic delta from the S-11 baseline: "non-regression: sub-agent population status match change ≤ 3 percentage points from S-11 baseline (i.e., overall match ≥ 93.8% if S-11 was 90.8%), and non-subagent population ≥ 97.1%." After Phase 1 fixtures pass 100%, run the audit on the owner's logs to establish an S-12 baseline before committing to the Phase 3 integration.

---
**Summary:** The S-12 plan is well-scoped and addresses a critical gap in subagent activity tracking, with a clear three-phase approach and measurable criteria. However, two blocking issues — non-deterministic merge ordering from non-monotonic timestamps and async agent race conditions — combined with five warnings (memory/ETag/truncation semantics, misattribution fallback, node-free compliance, audit target realism) mean the ≥97% status match target is contingent on careful implementation of the merge determinism, explicit cap application during streaming, and realistic baseline tracking. Phase size is appropriate (three focused phases) but the success criteria need explicit "known limitations" clauses for non-monotonic timestamp edge cases and async agent handling, plus a mid-phase baseline check after Phase 1 before Phase 2 integration.
