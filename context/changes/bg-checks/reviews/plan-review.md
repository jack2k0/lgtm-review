# Plan review: background checks (S-14)

Scope: plan.md vs `packages/core/src/{parse,analyze,steps,hints,schema,subagents,timing}.ts`.

1. **HIGH — the `pending` route is already gone when the notification arrives.** The background `tool_result` deletes its pending entry (`analyze.ts:412`) and only flips the flag (`:423`), so the plan's "`pending`/tool_use id route" (plan L34) cannot resolve the check. Also the plan's "never cleared on new prompt" is true but irrelevant here. Fix: on the background result, register `bgChecks: Map<backgroundTaskId, {check, prompt, thread, action}>` plus a second key by `tool_use id`, or a composite map; resolve the notification only through it. Add a test that the check object is still reachable after the prompt ended.

2. **HIGH — `resultSeq = notification seq` makes an edit during the run look checked.** `judge()` has no separate "edit after check" vs "last result" comparison: both the coverage test (`analyze.ts:227`) and the edit-count branch (`:243`) compare edits to `resultSeq` only. So an edit made after the background check started (seq 10) but before its notification (seq 40) satisfies `resultSeq > lastEdit` and the prompt is reported `checked`/`failing`, contradicting plan L34. Fix: add a `coveredSeq` (check `useSeq`, or the last event before the run) and use it for "did this result cover the last edit" (`:227`, `:243`); keep `resultSeq` only for `lastCompleted` selection and `incompleteAfter` (`:218-224`). Add `bg-check-edit-during.jsonl`: edit → bg check → notification ⇒ `unchecked` / "1 edit after last check".

3. **HIGH — the same `resultSeq` choice breaks the "latest verdict wins" rule.** A bg check started at seq 5 whose notification arrives at seq 40 becomes `lastCompleted` (`:217-220`) even if a foreground check passed at seq 25 on newer code; then a stale verdict overwrites a fresh one. Fix the ordering model first (finding 2), and pick the winner by coverage position, not arrival time. Add a fixture with a foreground pass after a bg start and a later bg failure notification.

4. **HIGH — steps will keep showing "no result".** The step's `ActionRec.check` is frozen at the background tool_result with `exitCode: null, passed: null` (`analyze.ts:444-455`); `checkTitle()` then prints "no result" (`steps.ts:140-144`). Updating only the analyzer `CheckRec` (plan L34/L36) never updates steps. Fix: store the `ActionRec` alongside the check in the bg map and rewrite `act.check` (+ excerpt/notRun) on the notification; add a `steps.test.ts` case starting from the existing `:227-234` background test.

5. **MED — the plan names a type that does not exist.** There is no `CheckResult`; the schema type is `StepCheck` (`schema.ts:147-154`), and the internal one is `steps.ts CheckRec` / `ActionRec.check` (`analyze.ts:394`). `CheckResult.background?` (plan L36) is unimplementable as written. Fix: `StepCheck.background?: boolean` (or an enum outcome) plus `checkTitle`/`checkOutcome` (`web/src/viewmodel.ts:192`) and its tests.

6. **MED — `failed` without an exit code has no representation.** `CheckRec.exit` is `number` (`analyze.ts:88`) and `judge()` always prints `failed (exit ${exit})` (`:235-239`); `StepCheck.exitCode` allows null but `checkTitle` falls through to "no result". Fix: make `exit` nullable or add `failedUnknown`, add a judge branch with the "background check failed" reason before `:235`, and a steps title branch; cover both with tests.

7. **MED — reusing `ignored` for `killed` hides the attempt and lies about the reason.** `judge()` drops ignored checks from `real` (`:215`), so a prompt whose only check was killed reports "no checks ran" (`:242`) rather than "stopped", and `lastCheckSeq` excludes it (`:162`). Fix: keep `completed=false` and add `resolved/stopped` that `incompleteAfter` (`:222-224`) skips but reporting still counts; extend `StepCheck`/`checkTitle` so "stopped" is renderable (there is no reason field today).

8. **MED — hint output will contradict the status.** `unchecked-edit` is driven by `lastCheckSeq` = `resultSeq` (`hints.ts:281-283`, `analyze.ts:160-163`). If finding 2 is fixed only in `judge()`, a prompt can be `unchecked` while no hint flags the uncovered edit. Fix both from the same `coveredSeq` source.

9. **MED — parser extraction must run before the non-prompt early returns.** `handleUser` returns for `origin.kind !== "human"` (`parse.ts:426-429`; real notifications carry such an origin — see `parse.test.ts:32`), and before that for `isMeta`/`isCompactSummary`/`scheduledTaskId` (`:424-425`), `sidechain` (`:423`), and tool_result records (`:419`). Plan L15 "any origin" is not enough. Fix: extract notifications immediately after the tool_result branch, and decide/document sidechain behavior (a notification in a subagent transcript is currently dropped or merged with no agent id; `subagents.ts:143-145,174-177` do not know the event type).

10. **MED — matching must verify the target is an unresolved background check.** A `<tool-use-id>` notification can otherwise overwrite a foreground completed check; and "first notification per task" dedupe (plan L29) is wrong for tool-use-id-only notifications and drops a later real completion after e.g. `killed`. Fix: only apply to `!completed && background` (records `background` on `CheckRec`), dedupe per resolved check, and prefer the first terminal status.

11. **MED — the plan will break an existing parser test.** `parse.test.ts:16-25` asserts that `<task-notification>` text yields `events === []`; emitting a `task-notification` event fails it, so "existing goldens/tests unchanged" (plan L53) is wrong. Fix: update that assertion (and `kinds()` expectations) in the same change.

12. **LOW — the plan's event shape invents a `seq` field the parser cannot supply.** Sequence numbers are assigned in `analyze.onEvent` (`analyze.ts:319`), not in `parse.ts`. Drop `seq` from the parser type (keep `ts`, `line`) or the analyzer and parser will disagree.

13. **LOW — `exitCodeOf` cannot parse the notification summary.** It only matches `^\s*(?:Error:\s*)?Exit code (\d+)` and deliberately discards exit 0 (`parse.ts:321-328`), while the summary is "(exit code 0)" mid-string. Write a separate case-insensitive matcher tolerant of `exit code: N` / "with exit code 1"; also make `status` matching case-insensitive (plan L28 only says that for the regex).

14. **LOW — timing semantics are unspecified.** The check phase is recorded from the launch result (`analyze.ts:435-437`) and the notification adds nothing, so `checkMs`/`durationMs` measure the launch, not the run, while the headline's check count changes with `ignored`. State the intended behavior and pin it in `timing.test.ts`/`steps.test.ts`.

15. **LOW — stale line references and missing test cases.** `CheckRec` is `analyze.ts:82-100`, not `:351-373` (that is tool_use creation). Missing tests: notification and tool_result in one record; notification before the result; two bg checks completing out of order; multiple/conflicting blocks in one record; missing both ids; unknown status; bg check in a subagent thread; killed-only-check reason; `testing/records.ts` has no notification builder.

Overall: the direction is right, but findings 1-4 mean the plan as written cannot resolve a background check end-to-end; the ordering rule in L34 must be restated in terms of a coverage sequence before implementation.
